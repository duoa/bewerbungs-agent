# Implementation Plan: Bewerbungs-Agent – CLI Job Application System

**Branch**: `001-bewerbungs-agent-core` | **Date**: 2026-04-07
**Spec**: [spec.md](spec.md)
**Input**: Feature specification from `/specs/001-bewerbungs-agent-core/spec.md`

## Summary

Build a CLI-based, modular job-application agent in Python that generates an
evidence-based cover letter and a tailored CV from a user's internal profile
(master profile, CV variants, personal skills, project docs, previous letters)
and a job description. The system uses a 12-stage structured-before-generative
LangGraph pipeline with typed Pydantic state at every boundary. It enforces
closed-world sourcing: every factual claim must be traceable to an approved
source; nothing may be invented. A starter-template + run-override configuration
model provides persistent defaults. Outputs are validated and rewritten
automatically on violation.

## Technical Context

**Language/Version**: Python 3.11
**Primary Dependencies**: LangGraph 0.2+, Pydantic v2, Typer, Anthropic SDK
(claude-sonnet-4-6), PyYAML, pypdf
**Storage**: Local files only — JSON, YAML, Markdown, PDF; no database
**Testing**: pytest, pytest-mock; Promptfoo for LLM evals (post-MVP)
**Target Platform**: Local CLI (macOS / Linux); no server deployment
**Project Type**: CLI application + library of pipeline stages
**Performance Goals**: Single run completes end-to-end in under 60 seconds on
typical hardware; no concurrent-user requirements
**Constraints**: All facts sourced from approved local files; LLM calls only
for structured extraction, planning, generation, and validation; no web access
at runtime
**Scale/Scope**: Single-user local tool; ~5 CLI commands; 12 pipeline stages;
3–5 test fixture job descriptions

## Development Environment

### Python Version

The project targets **Python 3.11** exactly. This pins runtime behaviour and

### Package Manager: uv

All environment management uses [`uv`](https://github.com/astral-sh/uv) — a
fast, lockfile-native Python package manager. No `pip`, `virtualenv`, or
`conda` in the project workflow.

### Bootstrap Steps

```bash
# 1. Install uv (once per machine)
curl -LsSf https://astral.sh/uv/install.sh | sh

# 2. Clone the repo
git clone <repo-url> bewerbungs-agent
cd bewerbungs-agent

# 3. Create a Python 3.11 virtual environment managed by uv
uv venv --python 3.11

# 4. Activate it
source .venv/bin/activate          # macOS / Linux
# .venv\Scripts\activate           # Windows

# 5. Install all dependencies (runtime + dev) from the lockfile
uv pip sync requirements-dev.txt

# 6. Install the project itself in editable mode
uv pip install -e .

# 7. Verify
python --version          # Python 3.11.x
jobagent --version
```

The project uses `python-dotenv` to load `.env` at CLI startup:

## Implementation Guidance

### Config Merge

`merge.py` implements:
1. Load `StarterTemplate` from YAML → validate into `StarterTemplate` model.
2. Apply `RunInput.overrides` (a `dict`) on top via recursive merge.
3. Validate merged dict into `MergedConfig`.
Merge precedence: `starter_template` keys < `run_overrides` keys.

### LLM Call Pattern

All stages that call the LLM use a two-function structure:

```python
def build_prompt(state: WorkflowState) -> list[dict]:
    # Pure function — assembles message list from state fields.
    # Testable without any mock.
    ...

def parse_response(response: ToolUseBlock) -> StagePydanticModel:
    # Pure function — validates LLM response into typed model.
    # Testable without any mock.
    ...

def stage_name(state: WorkflowState) -> dict:
    messages = build_prompt(state)
    response = llm_client.call(messages, tool_schema=StagePydanticModel.schema())
    return {"field": parse_response(response)}
```

The `llm_client` is injected via a factory so tests can substitute a mock.

### LangGraph Rewrite Loop

```python
def should_rewrite(state: WorkflowState) -> str:
    letter_ok = state.letter_validation.passed if state.letter_validation else True
    cv_ok = state.cv_validation.passed if state.cv_validation else True
    if (not letter_ok or not cv_ok) and state.rewrite_count < state.max_rewrites:
        return "rewrite"
    return "end"

graph.add_conditional_edges("validate_outputs", should_rewrite, {
    "rewrite": "rewrite_if_needed",
    "end":     END
})
graph.add_edge("rewrite_if_needed", "validate_outputs")
```

### Evidence Enforcement in `write_letter`

The writer prompt MUST receive only the `ContentPlan` serialised to JSON —
not the raw `InternalKnowledge` or `EvidenceMap`. This is the principal
mechanism preventing the LLM from accessing the full knowledge base at
generation time and inventing new facts.

### Validation Rules

Deterministic rules implemented in pure Python (no LLM):
- `source_compliance`: parse output text, check each fact phrase against
  `evidence_map.items[].claim`.
- `length`: `len(letter_draft.text)` vs `LengthMode` bounds.
- `redundancy`: count phrase occurrences using regex.
- `soft_skill_count`: count matched skill names from `content_plan.selected_soft_skills`.
- `must_not_mention`: scan for forbidden strings from `config.must_not_mention`.

LLM-assisted rules (optional, configurable per starter template):
- `tone`, `mode_rules`: pass draft + config.tone description to validator prompt.
